# 菜小智：现状调研与开发规划

调研日期：2026-09-28。状态：供讨论的规划草案，尚未实施。

## 1. 结论与范围

现有成果是“有视觉设计、有交互演示、有鸿蒙工程骨架”，尚不是已经接入真实 AI 并打通数据闭环的鸿蒙应用。适合沿用产品定位和视觉方向，逐步补齐原生能力与业务逻辑。

本次检查了当前目录中的说明材料、设计稿、网页源码、ArkTS 源码及工程配置，并阅读了用户提供的七张赛事截图。网页 JavaScript 已通过 `node --check` 语法检查；未运行浏览器交互测试，也未进行鸿蒙编译、签名和真机验证。当前 PATH 未发现 hdc、hvigorw，不能据此断定本机没有安装 DevEco Studio。

规划暂按“应用创新赛道、小团队、优先手机、云端模型允许使用”制定；赛程、设备、人员和经费尚待确认。截图是赛事参考材料，其中的推荐能力和优秀案例不等于本项目的必做功能。

## 3. 建议先聚焦的产品主线

优先服务“独居青年或两人家庭中的做饭新手”，集中解决一个问题：**手头有这些食材，在给定人数和预算下，今天怎么凑出一餐，少买、少浪费。**

建议主线：拍照或手动录入 → 确认食材 → 设置人数、预算与忌口 → 生成可执行的一餐 → 根据库存补齐清单 → 按步骤做菜 → 确认实际消耗并记录。

第一版建议限定少量常见食材和经过整理的家常菜谱，例如 20–30 种食材、15–20 道菜。数量只是讨论起点，以能验证的质量为准。

需要调整的产品承诺：

- 无校准依据时，不展示“98% 置信度”“96 分新鲜度”“88 分营养评分”等精确数字。识别结果允许用户更正；外观观察与食品安全判断明确分开。
- 没有可靠价格源时，先支持用户输入现场单价，计算整餐预算；示例价明确标注。参考价格后续须带地区、日期、单位和来源，删除无证据的“已核验”。
- 库存日期由购买日期、包装标示及用户录入驱动，不把固定“明天到期”当作真实推算。
- 完成烹饪后先确认实际消耗，再扣减库存，避免把计划用量自动当成真实消耗。

## 4. 技术选型

| 层次 | 建议选择 | 选择理由与边界 |
|---|---|---|
| 主客户端 | ArkTS + ArkUI + Stage，DevEco Studio | 延续现有工程，直接交付原生 HAP，方便接入鸿蒙能力；这是华为官方开发体系 [1] |
| SDK | 与目标真机匹配的稳定 HarmonyOS SDK | 不在设备未确认前锁死版本。截图参考 6.1，不代表所有能力已对所有机型开放；先编译最小工程再决定升级范围 |
| 本地数据 | ArkData RDB + Preferences | RDB 存食材、库存、方案、清单、记录；Preferences 存轻量偏好。官方区分了这些存储场景 [2] |
| 图像输入与联网 | Camera Kit／系统拍摄入口、相册选择、Network Kit | 第一版先完成可靠的图片输入和 HTTP 请求，自定义相机预览可后置；实际 API 以选定 SDK 为准 |
| 后端 | Python + FastAPI + Pydantic，单体服务 | 集中保管模型密钥、解析响应和执行规则；自动产生 OpenAPI，减少手写接口文档 [3] |
| AI | 优先试用阿里云百炼的千问 VL API | 官方提供图像理解和 HTTP／兼容接口 [4]；先用真实食材样本测效果、延迟和费用，再锁定具体模型与版本 |
| 推荐逻辑 | 菜谱数据 + 简单筛选排序 + 模型解释 | 程序处理忌口、库存、数量、预算约束；模型用于理解输入和说明推荐原因 |
| 部署 | 一个后端服务 + HTTPS + 环境变量配置 | 首版无需微服务、消息队列或独立管理后台；模型密钥不进入客户端 |
| 网页原型 | 保留现有 HTML/CSS/JS | 继续用于功能讨论与离线备用演示，避免同步维护第二套正式产品 |

FastAPI 是暂定首选；若团队主要熟悉 TypeScript 且没有 Python 经验，可改用 Node.js 单体后端，接口和客户端方案不变。当前没有依据需要自行训练模型、部署 GPU、引入 LangChain、多 Agent、向量数据库或复杂 RAG。

```text
ArkUI 页面
  → 页面状态与业务服务
    → 本地 RDB：库存、清单、菜谱、记录
    → HTTP：FastAPI
      → 模型适配：图片识别、需求理解、解释
      → 程序规则：约束检查、数量与预算计算
      → 精选菜谱与食材数据
```

先采用本地优先的数据方案，不做账号系统和家庭实时云同步。应用接续只传当前任务需要的状态，不把它当成完整的多设备数据同步。

建议的核心数据对象：`Ingredient`、`StockItem`、`Recipe`、`MealPlan`、`ShoppingItem`、`CookingRecord`。金额按分计算，食材数量明确克、毫升或个数及换算依据。

建议先保留三个后端入口：

```text
POST /recognitions  # 图片 → 食材候选、可见特征、需用户确认的信息
POST /meal-plans    # 人数、预算、偏好、库存 → 菜谱、用量、采购缺口
POST /assistant    # 当前菜谱与食材上下文 → 操作解释与回答
```

库存修改和完成记录优先在本地事务内处理。演示模式与真实模式显式区分；接口失败时不能悄悄返回固定番茄冒充真实识别。

## 5. 鸿蒙特色如何选择

截图写的是“建议集成 3 个及以上鸿蒙特性”，不是所给材料中的硬性三项门槛。建议规划三项，但每项先验证业务价值和接入条件。

| 顺序 | 候选能力 | 对菜小智的用途 | 实施前需要验证 |
|---|---|---|---|
| 1 | 桌面服务卡片 | 显示待买食材、优先消耗库存；点击进入清单 | 卡片更新与交互限制、实际 SDK 支持；普通卡片不能直接宣称实现截图中的高级互动动效 [5] |
| 2 | 应用接续 | 手机买菜后，将当前菜谱和步骤转到厨房平板 | 是否有两台兼容设备、同账号条件及状态恢复能力 |
| 3 | 实况窗 | 烹饪计时与当前步骤在锁屏等场景可见 | 应用类别准入、服务申请、后台计时和目标机型支持 |

接续或实况窗受限时，候选替代为购物清单系统分享、手机／平板自适应布局；其是否计入赛事特色数量需依据完整赛事规则确认。Camera Kit 和网络请求是基础能力，不直接当作三个特色的证明。

暂不选择 3DGS、FaceAR、3DToF、网络加速等：现有主线没有明确需求。隔空传送、碰一碰可在设备具备且确有分享需求时再考虑。

核验说明：本次成功取得华为开发体系、数据存储和卡片官方文档内容；截图中的接续、实况窗及 6.1 版本页存在访问失败或正文未加载情况。因此这里只列候选方向，不声称已确认最低 API、准入或全部设备支持。

## 6. 分阶段实施与验收

| 阶段 | 做什么 | 完成标准 |
|---|---|---|
| 0：确定范围 | 确认赛道、时间、设备、人员、预算；选定核心用户和主线 | 一版明确的必做与后置功能清单；用户确认后开始实施 |
| 1：鸿蒙工程跑通 | 用匹配 SDK 编译现有工程，补签名；验证图片输入和最小网络调用 | 真机能安装运行；记录构建环境；获得可演示 HAP |
| 2：真实数据闭环 | 拆分页面与服务，建本地数据，完成手动录入、菜谱、清单和库存记录 | 改人数会改用量；选不同方案会改清单；预算一致；重启仍保留数据；完成做菜会产生真实记录 |
| 3：接入 AI | 图片识别、人工更正、约束搭配、上下文问答 | 不同图片产生相应结果；识别失败能重试或手动输入；预算和忌口由程序检查 |
| 4：鸿蒙特色 | 先卡片，再根据设备和准入实现接续与实况窗 | 每项均能真机演示；不只停留在界面文案或权限声明 |
| 5：比赛交付 | 统一设计、精简说明、录视频、制 PPT、更新验证证据 | 提交材料与真实功能一致；线上主流程与明确标注的离线备用流程可演示 |

当前不承诺具体工期：先确定可投入人数、鸿蒙经验、截止日期和真机条件。阶段 1 是早期风险检查，不能拖到最后才尝试编译 HAP。

验证以关键链路为主：编译安装、人数与预算联动、方案切换、库存持久化、图片识别失败、断网处理、特色能力真机表现。模型试验建议从 20–30 张自行拍摄的不同光线食材图开始，记录识别结果、人工更正次数、响应时间和实际调用费用；这只能支持小样本结论。
